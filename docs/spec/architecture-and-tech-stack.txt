Desktop AI Task Assistant: Architecture &
Tech Stack Options
 Oct 12, 2026  ·  @Baranidharan Selvaraj
We are building a Windows assistant, opened with a global hotkey, that turns a chat
request into checked, confirmed actions in the user's connected tools. The MVP connects
to Jira, followed by Microsoft 365 and any MCP server. Before it acts, it asks questions
until it has real, validated values for everything it needs. This doc sums up the design so
far and compares the tech stacks we could build it with.

How a request flows
Every write goes through the same seven steps. Reads (status, search) skip steps 4 and 5
and answer straight away.
1. Open. The user presses the hotkey and types a request, e.g. "Create a bug for the login
page crashing on Safari, high priority, frontend team".
2. Understand and route. The assistant extracts the operation (create), the item type
(Bug), and each field along with how sure it is about it. It also decides which
connection the request is for (here: Company Jira).
3. Look things up. It fetches what the tool already knows: projects, required fields for a
Bug, allowed values, and people or components matching "frontend team". No
questions are asked for anything it can look up.
4. Ask. It asks one question at a time, with real choices plus a free-text box, until it has
enough information or the user presses Stop asking. After each answer it checks the
value, updates the draft, and picks the next most useful question.
5. Confirm. A confirmation card shows exactly what will be done, where, and which
values were assumed. The user confirms, edits or cancels.
6. Do it. The executor makes the change through the connection, acting as the user.
7. Report. The assistant replies with a link (e.g. WEB-1234) and writes an audit entry.
The user can type at any point to change details. A request that spans tools (create the
bug, then post it on Teams) becomes one plan with several steps, confirmed once.
The questionnaire
The questionnaire is our main differentiator. The assistant asks one question at a time,
with no limit, until every value it needs is real and checked, or until the user stops it.

How it asks:
Choices plus free text on every question. Choices are always real values from the tool
(allowed values, people, projects). A typed answer is matched to a real value. If it
matches several or none, the assistant asks a follow-up.
Never asks what it can look up. Project lists, people search and allowed priorities are
fetched, not asked.
Dependency order. Tool, then project, then issue type, then that type's fields, because
each answer changes what's required next.
Shows its working. A live draft panel next to the chat shows every field filled so far,
editable in place.
Remembers preferences. Usual project, components, assignees and Teams channels
are offered pre-selected, never applied silently.
Two profiles. Guided asks more questions, including quality questions. Expert asks
only blocking ones.
When the user presses Stop asking:
Gaps are filled only from real sources, in this order: the tool's default for the field, then
the user's saved preferences, then left empty (unassigned, no label).
Each filled value is labelled assumed on the confirmation card.
If a required field still has no real value, the card offers three options: answer just that
one question, save as a draft, or open the tool's own form with everything prefilled. The
assistant never invents a value to get past the tool's validation.

3. Sign in. OAuth opens the system browser, and tokens go straight into the Windows
credential store.
4. Test: "Connected as …" or a plain-language error.
5. The assistant caches the tool's projects, fields, teams and channels.
6. Name the connection and set defaults, optionally making it read-only.
Routing: which connection is a request for? The first check that gives a confident answer
wins:
1. The connection or product is named, or picked with an @ mention.
2. An ID in the message, e.g. WEB-123, belongs to one connection.
3. Only one connection can do this kind of task.
4. Keywords match, e.g. "sprint" for Jira, or "email" or "Teams" for Microsoft 365.
5. Otherwise the first question is "Which tool?", with the usual choice pre-selected.
Jira + Microsoft 365 workflows. Microsoft 365 is the people and collaboration layer next
to Jira. One request can cover the whole workflow. "Log a bug for the Safari crash, attach
the crash log from my OneDrive, and tell the frontend team on Teams" becomes three
steps, confirmed once:
1. Find the file in OneDrive, asking which one if two match.
2. Create the Jira bug with the file attached.
3. Post the message on Teams, with its full text shown on the card for approval.
The company directory also improves people questions, showing job title and
department. Each person's work email links them to their account in every tool.
Custom MCP connections cover tools we haven't built. A user can attach any MCP server,
remote or local:
Each server tool's input schema becomes the fields the questions are built from.
Tools not marked read-only are treated as writes, so they always need confirmation.
These connections are labelled "basic" because there are no lookups to offer real
choices.
A local server runs code on the user's machine, so it needs explicit consent.
Safety and the basics to handle
The rule behind all of these: the LLM proposes, the tool's own data decides. Nothing
reaches a tool unless it came from the user, a lookup, or the tool's schema.

Decisions so far
Eight design decisions are settled. The only open one is the LLM provider, which is part of
the tech stack choice below.
Two defaults were chosen, and either can be changed:
If the user stops with a required field missing, they can answer it, save a draft, or open
the tool prefilled.
Microsoft 365 comes before ServiceNow in the roadmap.
Still open: the LLM provider, and the company's rules on what data may leave the
machine.
Phases
The MVP proves the connections system and the questionnaire on Jira alone. Each later
phase adds reach.
1. MVP: hotkey, tray icon and chat. The full connections system (add, sign in, test, re-
auth, remove, several connections, routing). The Jira connector (Cloud and Data
Center). The questionnaire (question sources 1–6). Confirmation card and audit log.

Market position
Our edge is three things together: a Windows hotkey assistant, support for Jira Data
Center as well as Cloud, and checked questions plus confirmation before anything
changes. The biggest threat is general AI desktop apps with vendor MCP servers
becoming good enough.

mainly C#/.NET, and Option B if install size and memory matter more than build speed.
